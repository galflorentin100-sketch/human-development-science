# HDS — Canonical Engineering Contract

HDS is a scientific organization first and a practical human-development/training system second.

## North star
Research → construct → operationalize → measure → evidence → finding → claim → intervention → training → experience/data → analysis → transfer → retention → replication/review → improved knowledge → improved training.

The goal is not generic self-help, motivation, a chatbot, or impressive demos. The goal is scientifically defensible human development that becomes measurable training and improves through evidence.

## Non-negotiable scientific rules
- Never fabricate studies, citations, participants, measurements, statistics, sources, or missing values.
- Separate FACT, INFERENCE, HYPOTHESIS, and OPINION.
- Preserve uncertainty and contradictory evidence.
- Provenance is traceability, not efficacy.
- A proposed claim is not a supported claim.
- A training method is not supported merely because it is linked to a supported claim.
- Descriptive/observational data do not establish causality.
- Transfer and retention are measured, not assumed, whenever durable development is claimed.
- New evidence must trigger review/impact analysis, never silent rewriting of scientific state.
- AI may propose, synthesize, reason and research; governance decides scientific state.

## Engineering rules
1. Inspect the existing branch, schema, services and tests before changing architecture.
2. Continue from the existing implementation; never rebuild a subsystem unnecessarily.
3. Reuse existing governance services rather than duplicating them.
4. Every state transition must be explicit and auditable.
5. Every API needs validation, correct permissions and tests.
6. Every autonomous capability must respect permissions, approvals, cost controls, safety and idempotency.
7. Read-only analysis must remain separate from mutation.
8. Schema changes must be migration-safe.
9. Never report tests as passing unless actually executed.
10. Preserve stricter scientific behavior when components conflict.

## Continuation behavior
When asked to continue, proceed from the current roadmap without asking which small feature to build next unless a genuinely blocking scientific/product decision is required.

Default loop:
inspect → implement → test → fix → integrate → commit → continue.

## Definition of done
A feature is done only when behavior, failure paths, governance, permissions, auditability, adjacent lifecycle integration and tests are addressed. Do not add superficial product features while core scientific infrastructure is incomplete.
